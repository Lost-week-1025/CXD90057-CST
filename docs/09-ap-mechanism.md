# 09 · AP 机制探讨：Powerful 的实证与机型差异

> 本文回答三个问题：
> 1. 「AP」具体指什么
> 2. Powerful 的功能修改**实证**改了 AP 多少字节
> 3. 为什么不同机型可能是不同的 AP

---

## 1. 「AP」是什么

**AP = Application Processor 侧的应用层**，在 A6700 上具体落点是：

```
nflasha15（ext2 分区，673,741,824 B）
  └─ /lib/appFw.so（89,027,992 B，ELF aarch64 ET_DYN）
       ← 相机的主应用：菜单、UI、设置、成像流程
```

**为什么它叫「AP」而不是「固件」**：

| 层 | 载体 | 作用 | 改它意味着 |
|---|---|---|---|
| CP | `nflasha8`（vfat, 25,008,128 B） | 成像处理 | 改画面算法 |
| **AP** | `nflasha15` 的 `appFw.so` | **菜单、设置、UI** | **改功能可见性** |
| WBI | `nflasha5`（248,637,568 B） | 启动快照 | 改加载行为 |
| 内核 | `nflasha3` 的 `vmlinux.bin` | Linux | 改底层 |

**上层的功能解锁（FTP、快门帘、灵活曝光）几乎都落在 AP 层**，
因为「菜单是否出现」「设置是否允许」由 `appFw.so` 决定。

## 2. Powerful 的实证：改 AP 122 字节

来源：`_repos/a6700-powerful/sony-a6700-powerful-main/应用/docs/FEATURES.md`

### 2.1 六项功能的实测改动量

| 功能（本版状态） | **App 字节** | **WBI 字节** | **CP 字节** | 备注 |
|---|---:|---:|---:|---|
| 原生 FTP 菜单/开关/设置 | **89** | 151 | 0 | RAW+JPEG 上传有正向实测 |
| 关机快门帘及静音联动 | **9** | 21 | 0 | 正常关机闭帘有实测 |
| 灵活曝光 | **17** | 39 | 0 | 菜单已出现且可选 |
| 电子快门声音 | **2** | 4 | **1** | CP 在 `nflasha8` 扇区 11932 |
| 位移多帧合成（禁用） | 3 | 9 | 0 | 菜单待验收 |
| 动态增强防抖（禁用） | 2 | 4 | 0 | 实际功能未完成 |
| **合计（六项）** | **122** | **228** | **1** | 355 个字段定义 |

**关键观察**：

> **任何一项功能都要同时改 AP 和 WBI**，没有只改 AP 就能生效的。
> 唯一涉及 CP 的只有「电子快门声音」的 1 个字节。

### 2.2 为什么必须同时改 WBI

WBI 是**启动快照**（`sections=1314`，512 B 头）。它记录了：

- 每个分区的加载地址与长度
- 上次「已知良好」的运行时状态

**如果只改 AP 文件而不改 WBI**：

- 冷启动时 loader 按**旧快照**恢复 → 加载的是**旧段布局**
- 症状：文件改了但行为没变（或 AP 起不来）

**这就是为什么 FireHydrant 的 CineEI 补丁强调「必须先清 WBI 512 B 头」**。

### 2.3 三次独立交叉验证

| 数据 | Powerful | 本项目（CST） | 一致 |
|---|---|---|---|
| `app` 大小 | 89,027,992 | 89,027,992 | ✅ |
| `app` sha256 | `e65fd595…b0ef3` | `e65fd595…b0ef3` | ✅ |
| `cpapp` 大小 | 25,008,128 | 25,008,128 | ✅ |
| `cpapp` sha256 | `f12fa369…91ed` | `f12fa369…91ed` | ✅ |
| `wbi` 大小 | 248,376,320 | 248,637,568（分区） | ⚠️ 见下 |

**第三条需要解释**：

- Powerful 的 `wbi` 是**已解密且提取的 WBI2 逻辑内容**（248,376,320 B）
- 我们的 `nflasha5` 是**分区原始大小**（248,637,568 B）
- 差值 = `248,637,568 - 248,376,320 = 261,248 B`（分区头 + 对齐 + 尾部）

**所以两者不矛盾**：一个是被提取的逻辑内容，一个是物理分区。

## 3. 关键差异：文件偏移 vs ELF VA

**这是本项目最重要的技术区分之一。**

| 方案 | 地址类型 | 例子 | 优点 | 缺点 |
|---|---|---|---|---|
| **Powerful** | **文件偏移** | `0x4b7b93a` | 直接改文件，可离线重打包 | 无法表达运行时计算值 |
| **FireHydrant** | **ELF VA** | `0x2A02CE4` | 可定位代码逻辑 | 需先转文件偏移，超出文件范围时无效 |

Powerful 文档原文：

> `app` 是已解密 `/lib/appFw.so` 的 ELF **文件偏移**，不是 ELF 虚拟地址或分区偏移。

**这意味着**：

```
Powerful 的 0x4b7b93a  →  直接是 appFw.so 的字节位置
FireHydrant 的 0x2A02CE4 →  需要读程序头转成文件偏移
```

**我们在 EI 补丁里实测的转换结果**：

```
0x2A02CE4 → 文件偏移 0x2A02CE4（因为 LOAD 段 va=0, off=0，两者相同）
0x8D915E8 → 无对应（超出文件大小 0x54E6C98）
```

**为什么 RX 段 va == off**：`appFw.so` 的 `PT_LOAD` 第一个段 `off=0x0, vaddr=0x0`，
所以 RX 段内 VA 和文件偏移**数值相同**。

**但 RW 段不同**：`off=0x4489aa0, vaddr=0x4499aa0`（差 0x10000）。

**所以**：
- RX 段（代码）：VA 可直接当文件偏移用
- RW 段（数据）：VA 要减 0x10000

## 4. 不同机型可能是不同的 AP

### 4.1 为什么

`appFw.so` 是**按机型编译**的：

- 菜单布局（`.uxc` 文件）是按产品类型选的
- 功能可用性（`VAL_HAITA_*`）是编译进去的
- 所以不同机型的 `appFw.so` **内容和大小都不同**

### 4.2 我们手上的实际数据

| 机型 | SoC | `appFw.so` 大小 | sha256 | 来源 |
|---|---|---:|---|---|
| **A6700** | CXD90057 | **89,027,992** | `e65fd595…b0ef3` | 本项目实测 |
| **A7C2** | CXD90057 | **89,027,992** | `2ea02f7e…39b` | 本项目实测 |

**关键**：两个机型**大小相同，但哈希不同** —— 说明结构一样、内容不同。

**这解释了为什么跨机型不能照搬偏移**：

- 大小相同只是巧合（编译优化后对齐一致）
- 实际代码/数据位置完全不同
- 用 A7C2 的偏移改 A6700 = 改错地方

### 4.3 同 SOC 但不同「挡位」

| | FX30 | A6700 | A7C2 |
|---|---|---|---|
| SoC | CXD90057 | CXD90057 | CXD90057 |
| 产品类型 | `PRODUCT_MODEL_LAX`（Cinema） | `PRODUCT_MODEL_DZ`（消费级） | `PRODUCT_MODEL_DZ` |
| EI 菜单 | ✅ 本来就有 | ❌ 被裁掉 | ❌ 被裁掉 |
| 连拍菜单 | ✅ 本来就有 | — | — |

**同一个 SoC，AP 的差别只在「菜单是不是被编译进去」**。

### 4.4 版本差异

Powerful 文档的明确警告：

> 偏移只在 2.00 上成立。官方固件更新会同时覆盖三层，升级后必须重新确认落点，不要跨版本照搬。

**我们的实测也支持这点**：

```
A6700 v2.00  appFw.so  e65fd595…  (89,027,992 B)
A6700 v2.01  待验证（官方 v2.01 是否存在？索尼未发布 A6700 2.01）
```

**注意**：**索尼从未发布 A6700 的 2.01 官方固件**。
我们做的 `a6700_v201.DAT` 是**自己改版本号**的产物，
不是官方 v2.01。所以「A6700 2.01 的偏移」不存在。

## 5. AP 修改的三层联动

**Powerful 的实证最重要的一条**：

> 所有功能都同时改 `App` + `WBI`（个别还改 `CP`），
> 三层必须一起改，缺一不生效。

```
AP   appFw.so      菜单项、权限、可用性标志
WBI  nflasha5      启动快照里的运行时状态槽位
CP   nflasha8      成像处理参数（只有声音功能涉及 1 字节）
```

**改动量对比**：

| 层 | 六项合计 | 占比 |
|---|---:|---:|
| AP | 122 字节 | 35% |
| WBI | 228 字节 | 63% |
| CP | 1 字节 | <1% |

**WBI 反而改得更多** —— 因为运行时状态槽位比代码枚举多。

## 6. 对壳校验的影响

### 6.1 改 AP 会不会让固件包失效

**会，但只影响 `nflasha15` 的 CRC**：

```
改 appFw.so
  → 重算 nflasha15 的 ext2（若大小不变，只需改块内容）
    → 重算 part_image.sum 里 dev/nflasha15 的 CRC
      → 重算 L2（tar 内 .sum）
        → 重算 L3（帧校验）
          → 重算 L1（DEND）
            → 重算 header CRC32
```

**我们在 EI 补丁里完整跑通过这条链路**（`docs/06-rescue-and-ei.md` §5）。

### 6.2 改 WBI 会不会让固件包失效

**不会**。WBI 是**机身分区**，不在 `BODYDATA.DAT` 里。

`BODYDATA.DAT` 只含：
- `nflasha3`、`nflasha5`、`nflasha7`、`nflasha8`、`nflasha15` 作为 **tar 成员**
- 但 WBI 快照是**运行时生成**的，不是固件包的一部分

**所以**：
- 改 WBI（Powerful 的 228 字节）→ 不碰固件包
- 但 WBI 会**影响 AP 加载**（见 §2.2）

### 6.3 为什么 Powerful 走 USB 而不走 SD 卡

```
改 AP  = 89 MB 文件里的 122 字节
```

如果走 SD 卡更新包：
1. 要解 1 GB 的 `BODYDATA.DAT`
2. 改 tar 里的 `nflasha15`（673 MB）
3. 重算所有校验
4. **还要过 RSA**（执行层验签）

**而走 USB 服务通道**：
1. 直接读写 `/dev/nflasha15` 的固定扇区
2. 不需要重打包
3. 不需要过 RSA（走的是设备调试通道）

**这就是 Powerful 和我们的根本路径差异**：

| | Powerful | 本项目 v2.01 |
|---|---|---|
| 路径 | USB 服务通道写分区 | SD 卡更新包 |
| 需要过 RSA | ❌（设备通道） | ✅（但只到识别层） |
| 改什么 | 分区固定偏移 | 更新包内容 |
| 可回滚 | ✅（反向写） | 需官方包 |

## 7. 结论

1. **AP = `nflasha15` 里的 `/lib/appFw.so`**，是菜单与功能可见性的载体
2. **Powerful 实证**：六项功能合计改 AP 122 字节 + WBI 228 字节 + CP 1 字节
3. **任何功能都要同时改 AP 和 WBI**，只改一边无效
4. **Powerful 用文件偏移，FireHydrant 用 ELF VA** —— 前者可直接离线重打包，后者需转换
5. **RX 段内 VA == 文件偏移**（`off=0, vaddr=0`），RW 段差 `0x10000`
6. **不同机型 AP 内容不同**：A6700 与 A7C2 大小相同但 sha256 不同
7. **同 SOC 不同挡位**：FX30 是 `PRODUCT_MODEL_LAX`，菜单本来就含 EI/连拍
8. **A6700 没有官方 2.01**，我们的 `a6700_v201.DAT` 是自改版本号
