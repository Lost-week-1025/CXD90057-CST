# 05 · CXD90045 与 CXD90057 的壳校验变化与更新机制演进

> 本文对比两代平台的实测数据。CXD90045 数据来自 [`Lost-week-1025/CXD90045-FPSU`](https://github.com/Lost-week-1025/CXD90045-FPSU) 工作记录
> （ZV-E10 v2.03 / ZV-1F），CXD90057 数据来自本项目对 A6700 v2.00 的实测。

---

## 0. 结论摘要

**壳本身没变，变的是校验的执行位置。**

| | CXD90045 | CXD90057 |
|---|---|---|
| 容器/加密/三层校验 | — | **完全相同** |
| 校验由谁执行 | **PC 端** `FirmwareUpdaterEg.exe` | **相机端** `nflasha1` 的 updater |
| 通道 | PC 软件 + USB | **纯 SD 卡** |
| 结果 | 改包只需重算 CRC → 可过 | 多一道 RSA-2048 → 需换公钥 |

一句话：**"去 PC 化"把信任根从一台可被逆向的 Windows 程序，搬进了相机自己的引导环境。**

## 1. 实测数据对照

| 项 | ZV-E10 v2.03 | ZV-1F | **A6700 v2.00** |
|---|---|---:|---:|
| SoC | CXD90045 | CXD90045 | **CXD90057** |
| DAT 大小 | 372,454,920 | 443,505,056 | **1,024,017,848** |
| UDID 长度 | 188 (`0xBC`) | 84 (`0x54`) | **108 (`0x6C`)** |
| FDAT 记录 @ | `0xE4` | `0x7C` | **`0x94`** |
| 载荷起点 @ | `0xEC` | `0x84` | **`0x9C`** |
| **L1 存储 CRC** | `0x90BF49CC` | `0x9B12703E` | **`0xEABB5F09`** |
| **L1 重算 CRC** | `0x90BF49CC` ✅ | `0x9B12703E` ✅ | **`0xEABB5F09`** ✅ |
| 帧数 | 363,725 | 未测 | **1,000,017** |
| **帧 0 校验** | **不符**（存 `0x8D6E`，规则算 `0xB1F5`） | 未测 | **通过（bad=0）** |
| `part_image.sum` | **377 B** | 未测 | **454 B** |

> **UDID 长度在 20 / 84 / 108 / 188 之间跳动**——两代平台都一样，任何写死 FDAT 偏移的脚本都只能解一台机。

## 2. 三个真实差异

### 差异 1：帧 0 的规则 —— 两代不同

CXD90045（ZV-E10）实测：

```
帧 1          存储 0x77D9  通用规则 0x77D9   通过
帧 164636     存储 0x78BA  通用规则 0x78BA   通过
帧 0          存储 0x8D6E  通用规则 0xB1F5   ✗ 不符（原版即如此）
```

CXD90057（A6700）实测：

```
1,000,017 帧，bad = 0   ← 帧 0 也通过通用规则
```

**含义**：

| | CXD90045 | CXD90057 |
|---|---|---|
| 帧 0 | 特殊规则（或设备端不校验） | **遵循通用规则** |
| 全量重打包 | 帧 0 **不能**按通用规则重算，否则可能不通过 | 可全量统一重算 |

**工程影响**：CXD90045 时代的"只重算被改动帧、其余一字节不碰"这一保守做法，
在 CXD90057 上**不再是必须的**——A6700 的帧 0 与其余帧同规则，全量重算安全。

### 差异 2：更新通道 —— 从"PC 驱动"到"纯 SD 卡"

```
CXD90045:  PC(Windows) ─ FirmwareUpdaterEg.exe ─ USB ─ 相机
CXD90057:  SD 卡(BODYDATA.DAT) ─ 相机菜单「软件更新」 ─ 重启进 nflasha1
```

**CXD90045 的关键事实**（FPSU 工作记录）：

> 「校验代码需要相机连接才执行」——`FirmwareUpdaterEg.exe` 的 CRC 调用点在**连接相机后**才触发。

这意味着：CXD90045 的校验逻辑在 **PC 侧**，可以静态反汇编（VA `0x00402030`，4 个调用点链式分块，末尾 `not eax` 转标准 CRC-32）。

**CXD90057 没有 .exe**（A6700 只提供 SD 卡更新）。校验逻辑在 `nflasha1` 的 `initrd.img` 里，
而 `BODYDATA.DAT` **不含 `nflasha1`**（只含 nflasha3/5/7/8/15）。

### 差异 3：信任根的位置

| | CXD90045 | CXD90057 |
|---|---|---|
| 谁验 DEND CRC | PC 端 exe | 相机端（识别阶段：`appFw.so`） |
| 谁验 RSA | **无 RSA 环节**（PC 端只验 CRC） | `nflasha1` 的 updater |
| 改包门槛 | 重算 CRC 即可 | **需替换公钥** |

**这才是生态差异的根源**：CXD90045 时代"同目录放 DAT + 官方 updater 直接跑"就能过，
因为**校验端是一台你可以逆向、打补丁、甚至绕过的 Windows 程序**；
CXD90057 把校验端搬进了相机的引导环境，而那里有 RSA。

## 3. 更新机制演进

### 3.1 CXD90045：PC 主导

```
用户装 Sony 升级器 (Windows)
  → 连相机（USB 海量存储）
  → 升级器读 DAT、验 DEND CRC（连接后才执行）
  → 通过后驱动相机进入更新模式
  → 写入
```

**特征**：
- 校验（CRC）在 PC 端 → 可离线分析、可插桩、可绕
- 相机只是被动接受
- 无签名环节（或签名不参与判定）

### 3.2 CXD90057：相机主导

```
用户把 BODYDATA.DAT 放 SD 卡根目录
  → 菜单 → 设置 → 版本 → 软件更新
  → 【识别阶段】appFw.so 读包、验 DEND CRC、解密 header、比 model/版本 → 弹提示
  → 【执行阶段】重启进 nflasha1 → 验 RSA-2048 → 写分区
```

**特征**：
- 校验分两级：识别层（弱）+ 执行层（强）
- **识别层不验签**（本项目实测确认）
- **执行层验 RSA**（公钥在 `nflasha1`，不在包内）

### 3.3 为什么会这样变

推测（标注为推断）：
1. **攻击面收缩**：PC 端 exe 是可执行文件，易被逆向/打补丁；相机引导环境不可随意修改
2. **流程简化**：SD 卡更新不需要装软件，跨平台
3. **代价**：把 RSA 引入 = 自制固件门槛从"写脚本"变成"换公钥"

**副作用**（对本项目最重要）：**识别与执行分离**，创造了"能提示 ≠ 能刷"的中间态。

## 4. 安全边界变化

| 边界 | CXD90045 | CXD90057 |
|---|---|---|
| 第一道 | DEND CRC（PC 端） | DEND CRC（`appFw.so`） |
| 第二道 | `.sum`（相机端，推断） | `.sum`（相机端，推断） |
| 第三道 | 帧校验 | 帧校验 |
| **第四道** | **无** | **RSA-2048（`nflasha1`）** |
| 绕过难度 | 重算 CRC | 替换 `nflasha1` 公钥 |

**关键**：前三道都是可重算的 CRC/求和——**它们只防传输损坏，不防篡改**。
真正防篡改的只有第四道，而它**只在执行阶段出现**。

## 5. 对改机路径的含义

| 路径 | CXD90045 | CXD90057 |
|---|---|---|
| 改固件刷入 | ✅ CRC 重算即可 | ❌ 需换公钥 |
| 运行时补丁（RAM） | 可行 | 可行（USB 服务通道） |
| SD 卡开机 hook | ✅ `ld.so.preload` 可写 | ❌ `/etc` 在只读 rootfs |
| 服务模式降级 | — | 机制存在（`up.sh ver`），入口待打通 |

**两代共同点**：真正实用的改机路径从来不是"刷自制固件"，而是**绕过固件**——
CXD90045 走 preload hook，CXD90057 走 USB 服务通道 + 可能的 mode 切换。

## 6. 仍缺的一环

CXD90057 的 RSA 公钥实体未取得。A6700 无 .exe，唯一路径是 fastboot 只读
`nflasha1`（24 MiB）后解析 `initrd.img:/etc/VerificationKey.pem`。
在拿到之前，"刷自制固件"这条路对 A6700 是封闭的。
