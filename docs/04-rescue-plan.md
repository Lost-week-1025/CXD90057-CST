## 1. 核心模型：版本三元组

| # | 载体 | 位置 | 谁写 | 状态 |
|---|---|---|---|---|
| ① | 包声明版本 | `FdatHeader` @0x21(major)/0x20(minor) | 重打包方 | 实测可控 |
| ② | 相机当前版本 | `/setting/updater/dat4` | updater / `up.sh modver` | ❓ 未验证 |
| ③ | 菜单显示 | 未知（读 ① 还是 ②） | — | ❓ 未验证 |

证据（`/bin/up.sh`）：

```sh
ud_datcnv.elf -d -i /setting/updater/dat4 -o /tmp_updater/upcurver -a
_current=`cat /tmp_updater/upcurver`
```

**推论**：识别阶段的"2.00 → 2.01"提示，是 ①（包）与 ②（`dat4`）比较的结果。
**能否回滚，取决于 ② 是否被回写**——而不取决于 ①。

### 1.1 实验判读矩阵

用"声明 2.01 / 内容 2.00"的包测试后，同时记录 ② 与 ③：

| `dat4`(②) | 菜单(③) | 含义 |
|---|---|---|
| 不变 | 不变 | updater **未回写**版本 → 官方 2.00 仍可刷 |
| 变 2.01 | 变 2.01 | updater **回写**了 → 需 Version Skip 才能降级 |
| 不变 | 变 2.01 | 菜单读包内 `FdatHeader`，与 `dat4` 解耦 |
| 变 2.01 | 不变 | 显示有缓存 → 需二次重启复核 |

**没有 ② 的原值，此实验无法判读。**

## 2. 救砖分级

| 级 | 手段 | 前置条件 | 状态 |
|---|---|---|---|
| **R0** | 官方 SD 卡刷 `BODYDATA.DAT` | 相机能进菜单 | 已具备 |
| **R1** | `up.sh ver` / `up.sh modver` | 一次 shell | 机制已知，入口待打通 |
| **R2** | fastboot 写 | 需扩展载荷（写命令） | 未实现 |
| **R3** | 拆机 / 送修 | — | — |

**优先级 R0 → R1 → R2 → R3。** R2 只在 R0/R1 均不可用时才有意义。

## 3. R1 安全性分析

`/bin/up.sh` 提供（`UPDIR=/setting/updater`，`/setting` = `nflasha2`，vfat 可写）：

| 命令 | 写入内容 | 是否碰 `dat4` |
|---|---|---|
| `up.sh ver` | 两个**空文件**（`mode`、`mode6`） | ❌ |
| `up.sh modver XXXX` | **覆盖写** `dat4` | ✅ |
| `up.sh serv` | 两个空文件（`mode`、`mode3`） | ❌ |
| `up.sh` | `mode` + `mode1` | ❌ |

### 3.1 两个关键差异

**① 原子性**：`func_modver` 用

```sh
ud_datcnv.elf -e -i /tmp_updater/upnewver -o /setting/updater/dat4 -a
```

**直接覆盖目标文件**，无 `.tmp` + rename。写入过程断电 = `dat4` 半写。

对比上游工具链的做法（`fl23_files.c`）：

```c
/* Upload is append-only into O_EXCL .new, complete SHA checked before
   atomic rename. Unknown existing content is never replaced or deleted. */
```

**官方脚本的安全性低于社区实现**——这是评估时的关键不对称。

**② 写入量**：`ver` 只 `touch` 空文件；`modver` 改写有结构的记录文件。

### 3.2 风险分级

| # | 风险 | 后果 | 等级 |
|---|---|---|---|
| 1 | `dat4` 半写/损坏（断电） | 版本记录无效 | 中 |
| 2 | `dat4` 合法但错误 | 版本比较异常 | 低 |
| 3 | `/setting` vfat 元数据受损 | 设置异常，通常可重建 | 中低 |
| 4 | **启动路径依赖 `dat4`** | 若依赖 → 可能卡启动 | **未知（待查）** |
| 5 | `/tmp_updater` 挂载失败 | 脚本自身报错 | 极低 |

第 4 项是唯一可能导致"真砖"的路径。

### 3.3 与固件级写入的对比

| 操作 | 分区 | 写坏最坏后果 | 兜底 |
|---|---|---|---|
| `appFw.so` 补丁 | `nflasha15`（AP 根） | 主程序起不来，USB/菜单一起失效 | ❌ |
| `up.sh modver` | `nflasha2`（`/setting`） | 版本记录异常 | ✅ 备份 / R0 |
| `up.sh ver` | `nflasha2`（`/setting`） | 模式文件未建成 = 无效果 | ✅ 删文件 |

**结论：救砖方案本身不应引入新的砖风险。`up.sh ver` 满足，`modver` 需备份为前提。**

## 4. 静态取证清单（全部无需相机）

按优先级。工具：`src/parse_nflasha1.py`、`tools/locate_string_owner.py`、`tools/disasm_helper.py`。

### 4.1 第一优先：`dat4` 的读写方

| 项 | 查什么 | 在哪查 | 判定依据 |
|---|---|---|---|
| **P1** | 谁**读** `dat4` | `nflasha15` 全镜像搜 `dat4`、`/setting/updater` | 引用它的二进制的**加载路径**：若只有用户态服务 → 风险低 |
| **P2** | 是否在**启动路径** | 引用者的 `.so` 是否出现在 `libIMDB.so` 的服务表 | 在表内 = 开机加载 = 需评估 |
| **P3** | bootloader 是否读 | `nflasha1` / `nflasha7` 内搜 `dat4` | 若 bootloader 读 → 风险升级 |
| **P4** | `dat4` 的格式 | 已提取的 `dat4` 样本 + `ud_datcnv.elf` 反汇编 | 确认是否含校验字段 |

**判读**：若 P1/P2 显示只有 `up.sh` 与 updater 使用，且 P3 为否，则
`modver` 的风险可从"中"降到"低"。

### 4.2 第二优先：updater 的验签行为

| 项 | 查什么 | 判定依据 |
|---|---|---|
| **U1** | RSA 验签发生在**哪一步** | updater 二进制中的调用序列：解包前 / 写分区前 |
| **U2** | 失败时**是否已写**部分分区 | 验签与写操作的先后顺序（控制流） |
| **U3** | 是否存在 `.sum` 之外的第四层校验 | 搜 `startupdate.sh` / `endupdate.sh` 的校验调用 |

### 4.3 第三优先：bootloader 退化行为

| 项 | 查什么 | 判定依据 |
|---|---|---|
| **B1** | `/setting/updater/mode*` 读不到时的默认行为 | `nflasha1` 的 boot 相关脚本/配置 |
| **B2** | WBI 快照失效时是否自动回落 updater | 同上；决定 AP 损坏能否自救 |
| **B3** | `kemco.txt` 支持哪些内核参数 | 是否存在 `init=` / `rdinit=` 类可覆盖入口 |

### 4.4 第四优先：公钥

| 项 | 查什么 | 判定依据 |
|---|---|---|
| **K1** | `nflasha1` 内是否存在 `VerificationKey.pem` | 目标 SHA-256 `8281413b…c6c2e2`，451 B |

> K1 的价值**低于** P1–P3 与 U1–U3：公钥只能"验别人给的包"，
> 而 P/U 组决定"自己做的事安不安全"。

## 5. R2：最小写入设计（规划，未实现）

若 R1 不可用，才考虑 fastboot 写。原则：**写最小范围**。

### 5.1 首选目标：WBI 头 512 B

依据（实测记录）：

```
nflasha5 = 248,637,568 B   Warm Boot Image
偏移 0..511               struct wb_header
  magic = "WBI2", sections = 1314
  校验和未启用            ← 关键：头失效即弃用快照
```

| 场景 | 清 WBI 头的结果 |
|---|---|
| WBI 损坏导致起不来 | 强制重建快照（修复方向） |
| AP 正常 | 等效一次冷启动（正常行为） |
| AP 也损坏 | 仍起不来（未变坏） |

**写入量对比**：清头 512 B ／ 刷 WBI 248 MB ／ 刷 AP 673 MB。

### 5.2 开发前提（任一不满足即不得开发）

1. R1 已确认不可用
2. 已完成 §4.1–4.3 全部静态取证
3. 已有完整只读备份（含独立回读校验）
4. 已具备写后逐字节回读比对能力
5. 上游明确接受"实验性模块、默认禁用"

---

## 6. 验证顺序

```
① 只读基线：nflasha1(24 MiB) + B0/B1(各4 MiB) + nflasha5 头 512 B
② 静态取证：§4.1(P1–P4) → §4.2(U1–U3) → §4.3(B1–B3)
③ 判定 R1 可行性（能否取得 shell）
④ 仅当 ①②③ 齐备，才评估 R2
```

**在 §4.1 结论出来之前，`up.sh modver` 应视为"中风险、后果部分未知"。**

---

## 7. 上游贡献建议

按风险从低到高：

1. `parse_nflasha1.py`（纯离线解析）— 可独立合并
2. 基准记录工具（`dat4` / WBI 头 / 分区哈希采集）— 只读
3. R1 编排（`ver`/`modver` 封装，带写前读+写后校验）— 需上游同意
4. R2 载荷 — 仅作实验分支、默认禁用

> 上游 `AGENTS.md:28`：「硬件路线只提供引导与已知区间备份，不扩充未验证全盘恢复」。
> 因此 R2 不进入默认路径是**尊重上游既有边界**。
