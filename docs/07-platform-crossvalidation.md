# 07 · 平台交叉验证：CXD90045 / CXD90057 / FX30 BK4

> 本文把三处不同来源的校验机制放在一起对照，避免把「固件壳校验」和「设置容器校验」混为一谈。

---

## 1. 三个对象，三套校验

| 对象 | 所在层 | 校验方式 | 数据来源 | 我们是否实测 |
|---|---|---|---|---|
| **CXD90045 固件壳** | PC 端 `FirmwareUpdaterEg.exe` | zlib CRC-32（`not eax` 转标准），4 个调用点链式分块 | `Lost-week-1025/CXD90045-FPSU` | 采信上游数据 |
| **CXD90057 固件壳** | 机身 `appFw.so`（识别）+ `nflasha1`（执行） | L1 DEND CRC-32 + L2 tar `.sum` + L3 分帧 sum16 + RSA-2048 | 本项目实测 | **全层实测 PASS** |
| **FX30 BK4 设置容器** | 机身 `/setting/` 下的设置镜像 | `bank+0x20 = sum(bank[:0x20]) + sum(bank[0x24:])` | `Lincan19540/fx30-firmware-research` | 采信上游数据 |

**关键**：三者不是同一个东西。
- 前两个是**固件更新包**的完整性校验
- 第三个是**机身设置分区**的校验和

所以：**「FX30 能成对改 BK4 字节」不能证明「A6700 的固件壳可改」**，反之亦然。

## 2. CXD90057 固件壳（本项目实测）

```
L0  容器链       DATV · PROV · UDID · FDAT · DEND
L1  DEND CRC-32  覆盖 [0, N-12)，大端
L2  tar .sum     NN01_*_sum/*.sum 文本清单，逐文件 CRC-32
L3  帧校验       1024 B 块，sum16 = Σ(511 × u16le) & 0xFFFF
    RSA-2048     覆盖整个 FDAT 载荷，识别层不验、执行层验
```

**A6700 v2.00 实测数值**：

```
文件大小      1,024,017,848
FDAT 载荷     1,024,017,680 = 1,000,017 × 1024 + 272
L1 DEND       0xEABB5F09
L3            1,000,017 帧，bad=0，endflag=1
Header CRC32  0x5D0B3237
L2            9 清单 / 88 条目 / 88 通过
model         0x20030001
```

**改动后（v2.01）重算数值**：

```
L1 DEND       0x5F8FFD51   （重算后自洽）
L3            1,000,017 帧，bad=0，endflag=1
Header CRC32  0x9FD7F650
L2            9 清单 / 88 条目 / 88 通过（tar 内容未动）
```

## 3. CXD90045 固件壳（对比参照）

来自 `Lost-week-1025/CXD90045-FPSU`：

- 校验逻辑在 **PC 侧** `FirmwareUpdaterEg.exe`（VA `0x00402030`）
- 4 个调用点链式分块，末尾 `not eax` 转标准 CRC-32
- 同样有 1024 B 帧块求和 + `.sum` 文本清单

**与 CXD90057 的差异**：

| 维度 | CXD90045 | CXD90057 |
|---|---|---|
| 校验位置 | PC 端 exe | **机身 `appFw.so` / `nflasha1`** |
| 可静态反汇编 | ✅（exe 在 PC 上） | ⚠️（要解固件才能拿到） |
| 签名 | 文献未提及强 RSA | **RSA-2048** |
| 生态影响 | 同目录放 DAT + 官方 updater 直接跑就能过 | 需要先过机身识别层 |

**这就是「去 PC 化」的实质**：校验从**可逆的 PC 程序**搬到了**机身内嵌程序**，
且加了 RSA。所以 CXD90045 时代「改个 exe / 摆个文件」的做法在 CXD90057 上不成立。

## 4. FX30 BK4 设置容器（不同层）

来自 `Lincan19540/fx30-firmware-research`（CC BY-NC-SA 4.0），
实测代码在 `code/fx30_burst.py`（597 行，2026-10-26 实机验证）。

**容器格式**：
- magic `BK4\0`
- 设置分 bank 存放，**校验和偏移 `PFUNC_ADJ = 0x40`**（不是 `+0x20`）
- 规则：`bank+0x40 = sum(bank[:0x40]) + sum(bank[0x44:])`（跳过自己的 4 字节）

**可改的两个 enum-index 字节**（都在 **bank0**，`< 0xd2560`，共 2 字节）：

| 偏移 | 枚举表 | 属性 ID | 写入值 | 语义 |
|---|---|---|---|---|
| `0x8EF80` | `EXTERN_VAL_DRIVE_MODE_*` | `0x02cf013b` | `0x01` | `BURST` |
| `0x91690` | `DRIVE_MODE_*` | `0x02cf02ae` | `0x01` | `CONT_SHOOTING` |

**这两个字节不是属性 ID，而是两张枚举表的 0-based 位置**。

**必须成对写**：它们是同一设置的两层表示，**只写一边会被固件回退**。

**安全流程**（上游的框架）：
```
snapshot → dry-run → write → readback → auto-rollback
```

**冷启动要求**：设置是**暖启动镜像**，改完必须**拔电池 ≥30 s** 冷启动（热重启会还原）。

**上游已经排除的方向**（`fx30_burst.py` 注释）：

```
已移除（错误方向）：0x915D2..0x915D7 —— 属性 0x02cf0273 与连拍无关
已移除（实测证伪）：
  · 「7 字节等值组」28 字节 —— 是 PDT 打包对齐的巧合，不是语义数组
  · 6 条"静态能力标志"（0x02cf02ce/cf、0x02cf0350/51、0x02cf04b7/b8）
    —— 实机成对写入后菜单无任何变化

结论：菜单可见性不在 BK4 属性层。
```

**最后这句话是本项目最重要的交叉验证结论之一**（见下一节）。

### 与固件壳的区别

| 对比项 | 固件壳（CXD90057） | FX30 BK4 |
|---|---|---|
| 校验对象 | 更新包 `BODYDATA.DAT` | 机身设置分区 |
| 校验算法 | zlib CRC-32 + sum16 + RSA | `sum(bank) + sum(bank[0x24:])` |
| 触发时机 | 更新时 | 每次设置写入 |
| 改错后果 | 更新被拒（安全） | 设置丢失 / 开机异常 |
| 是否可离线复算 | ✅ 全部可算 | ✅ 全部可算 |

**两者唯一的共同点**：都能离线重算校验和。
**但「能重算」不等于「能绕过签名」** —— 固件壳的执行层有 RSA，BK4 没有。

## 5. 交叉验证带来的三个结论

### 结论 1：壳校验的层次在不同平台上会「搬家」

| 平台 | 壳校验在哪 |
|---|---|
| CXD90045 | PC 程序里 |
| CXD90057 | 机身运行环境里（识别层）+ 更新环境里（执行层） |

**这解释了为什么社区对「能不能改固件」的说法长期不一致**：
拿着 CXD90045 时代的经验（改 PC 程序）去套 CXD90057，自然会失败。

### 结论 2：识别层与执行层的分离是 CXD90057 的关键设计

```
识别层  appFw.so     读 FdatHeader[32:34] 比对版本    ← 不验 RSA（已真机确认）
执行层  nflasha1     updater 验 RSA-2048 后写 flash   ← 验 RSA
```

**所以「SD 卡放改动版能弹提示」是必然的**，不是漏洞，是分层设计的结果。

### 结论 3：设置容器校验（BK4）与固件壳校验互不影响

BK4 的 `sum(bank[:0x40]) + sum(bank[0x44:])` 只管**设置分区**，
跟 `BODYDATA.DAT` 的三层校验没有交集。

**这意味着**：
- 改设置（BK4）**不会**让固件包失效
- 改固件包**不会**让设置失效
- 但两者都改了之后，需要**分别**验证

### 结论 4（最重要）：菜单可见性不在设置层

FX30 的上游研究给出了一个**反向排除**的结论：

> 6 条"静态能力标志"（`0x02cf02ce/cf`、`0x02cf0350/51`、`0x02cf04b7/b8`）
> —— 实机成对写入后菜单无任何变化，已逐一排除。
> **结论：菜单可见性不在 BK4 属性层。**

**这与 A6700 的 EI 情况完全一致**：

| 平台 | 改了设置层 | 菜单是否出现 | 真正的位置 |
|---|---|---|---|
| FX30 | BK4 两个 enum-index 字节 | ✅ 出现（连拍） | **这个功能本来就是「值」不是「开关」** |
| FX30 | BK4 六个能力标志 | ❌ 不出现 | 不在 BK4 |
| A6700 | `appFw.so` 9 处（EI 计算层） | ❌ 不出现（预期） | 需要 Step 1/2 的计数表 |

**所以「菜单显隐」和「功能值」是两层东西**：

```
功能值      BK4 属性 / flash 设置            ← 可改，改完持久化
菜单显隐    appFw.so 的 PRM/VAL 派生可用性    ← 编译进代码，不是设置项
```

这解释了为什么：
- **FX30 改 BK4 能让连拍生效** —— 连拍在 FX30 上**菜单本来就可见**，BK4 只是改「值」
- **A6700 改 appFw.so 不能让 EI 出现** —— EI 的菜单项被 `VAL_HAITA_*` 挡着，那不在设置层

**这条结论直接决定了救砖/解锁的路径选择**：
> 想改「行为」→ 改设置层（BK4 / flash 设置），风险低、可回滚
> 想改「菜单可见性」→ 必须动 `appFw.so` 或其加载的数据段，风险高、必须过壳校验

## 5.5 FX30 与 A6700 是同 SOC 但不同「挡位」

| | FX30 | A6700 |
|---|---|---|
| SoC | CXD90057（同代） | CXD90057 |
| 产品类型 | **Cinema Line**（`PRODUCT_MODEL_LAX`） | 消费级（`PRODUCT_MODEL_DZ`） |
| EI/连拍 | 菜单里**本来就有** | 菜单里**本来就没有** |
| 社区做法 | 改 BK4 值 | 改 `appFw.so` 派生可用性 |
| 难度 | 低（2 字节 + 校验和） | 高（211 段 / 827 B + 程序头） |

**同一个 SoC，差别只在「菜单是不是被编译进去」**。
FX30 是 Cinema Line，EI 菜单是产品定义的一部分；A6700 是消费级，EI 代码在但菜单被裁掉。

**这也说明**：`PRM_FEATURE_MANAGER_menu_item` 返回的 `TYPE_MENU_ITEM_LAX` 不是「功能开关」，
而是**选择哪套编译好的 `.uxc` 布局**。FX30 和 A6700 挂的是不同的布局文件。
