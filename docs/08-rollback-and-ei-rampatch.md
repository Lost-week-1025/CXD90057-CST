# 08 · 2.01 回滚方案 与 EI 的正确路径

> 本文回答两个问题：
> 1. 我们做的 v2.01 改动版怎么回滚
> 2. 为什么 EI 测试固件的**文件补丁版**不下放，而**RAM 补丁版**才是正道

---

## 第一部分：v2.01 改动版的回滚

### 1.1 先分清三种「改动」

| 改动类型 | 载体 | 断电后 | 回滚难度 |
|---|---|---|---|
| **A. 版本号改动**（`a6700_v201.DAT`） | SD 卡上的独立文件 | 相机**从未被改** | 无（拿走 SD 卡即可） |
| **B. 文件补丁**（`a6700_v201_ei.DAT` 里的 9 处） | 若刷入则改 `nflasha15` | **持久化** | 需重刷官方包或反向写 |
| **C. RAM 补丁**（FireHydrant 的 Step 0–8） | 进程内存 | **自动消失** | 断电 10 s |

**关键**：A 类根本没有改动相机。我们只把它放到 SD 卡上，让相机**读取并识别**，
没有点「执行」，所以 `nflasha15`、`nflasha5`、`appFw.so` 一个字节都没变。

**所以 A 类不需要回滚** —— 拔掉 SD 卡，相机就是出厂状态。

### 1.2 如果真刷了改动版（B 类），回滚阶梯

**前提**：改动版 RSA 签名失效，正常更新流程**不会接受**它，
所以「刷进去」这一步在现有 fastboot 工具下**做不到**。
下面阶梯是为「一旦有了写入能力」准备的安全网。

| 级别 | 手段 | 需要什么 | 有效性 |
|---|---|---|---|
| **R0** | SD 卡放官方 `BODYDATA.DAT` 重新更新 | 仅 SD 卡 + 相机能启动 | ✅ 覆盖整份 AP，最干净 |
| **R1** | `up.sh ver` / `up.sh modver` | 相机 shell（Powerful 等路径） | ⚠️ 只影响识别层，改不了已写入的 AP |
| **R2** | 反向写 827 B 到 `appFw.so`（FL23 基线） | USB 服务通道 + PMCA 认证 | ✅ 有 FireHydrant 的现成模块 |
| **R3** | 写回 512 B WBI 头备份 | USB 服务通道 | ✅ 恢复旧快照启动 |
| **R4** | 官方恢复包 / 返厂 | — | ✅ 兜底 |

**顺序**：R0 → R2 → R3 → R4。R1 只在「相机还能启动但识别异常」时有用。

### 1.3 FireHydrant 已经给了完整工具链

`_rt/firehydrant/FireHydrant-main/wbi/` 里五个模块，正好覆盖回滚：

| 模块 | 编号 | 功能 | 验证判据 |
|---|---|---|---|
| `wbi_hdr_block.c` | 211 | 只读 88 B 头 + 分区采样 | `magic=57424932`（`WBI2`）、`sections=1314`、`sector=512` |
| `wbi_rewrite_block.c` | 212 | **原样写回 512 B**（写通道自检） | `write=512`、`verify=OK` |
| `wbi_clear_block.c` | 213 | 备份 + 清零 512 B | `pre=512 backup=ok write=512 fsync=0 zero=1` |
| `wbi_restore_block.c` | 214 | 从备份写回 | `write=512` |
| `ap_fl23_revert_block.c` | 215 | 程序头 `0x4489230 → 0x4488EED` | `pre=16 write=16 read2=16` |

**最关键的 212 `rewrite`**：它是**写通道自检** —— 写回原样数据，
如果 `verify=OK` 说明写通道可用，否则**不要做任何真正的修改**。

**这个自检是防砖的第一道闸**，比任何补丁都重要。

### 1.4 回滚的硬约束（FireHydrant 明确写的）

```
1. 清头后不再有快照保护，回退只能靠 USB 通道或官方恢复包
2. 只在完整断电后才生效，热重启看到的仍是旧状态
3. 不要在 BIS / 固件更新流程里用它关机
   —— 那条路径会走 warm 并可能重建快照
4. clear 前确认备份已经落到主机（脚本会打印 orig512=）
5. apfl23 改的是加载器读的程序头，写坏会让 AP 起不来
```

**第 3 条最重要**：如果通过「BIS / 更新流程」关机，会走 `warm` 挂起并**重建 WBI 快照**，
把你清的 512 B 又写回去 —— 等于白做。

**正确做法**：改完立刻**拔电池**，不要用菜单关机。

## 第二部分：EI 打开的正确路径

### 2.1 两种方案的本质区别

| | 文件补丁（我们做的） | **RAM 补丁（FireHydrant 的 Step 0–8）** |
|---|---|---|
| 改什么 | `appFw.so` 文件内容 | AP 进程内存 |
| 需要过壳校验 | ✅ 要（L1/L2/L3 全重算） | ❌ 不需要 |
| 需要清 WBI 头 | ✅ 要（段布局变了） | ❌ 不需要 |
| 断电后 | **持久化** | **自动消失** |
| 失败后果 | AP 起不来 | 重启即恢复 |
| 适用场景 | 长期固化 | **研究/验证** |

**结论：验证 EI 功能应该用 RAM 补丁，不是文件补丁。**

### 2.2 FireHydrant 的 Step 0–8 是完整的 RAM 方案

来源：`_rt/firehydrant/FireHydrant-main/cine_ei/rampatch/README.md`

| Step | 内容 | 主要落点 | 备注 |
|---|---|---|---|
| 0 | Base ISO/EI 入口、底栏 EI 文字、99 段 UI | 显示位 `0x38180DA`（`00 → 01`） | 可选；Step 2 需要 |
| 1 | Log shooting 四项可选 | 值节点能力列 + `persist_unit+0xB/+0xC` + 项目状态 | 不调 setter、不写 flash |
| 2 | Base ISO/EI 面板解除禁止 | 7 个支持标志 + **114 对**计数/限制 | 只动 Cine EI 相关项 |
| 3 | HIGH 基准 12800 → 2500 | `0x8D915E8`、`0x8D915EC`（u32 `26 → 19`） | 两份必须一致 |
| 4 | 标题读取 Base 阶梯 | `0x2A02CE4`、`0x2A02D6C`、`0x2C55DDC`、`0x2C55E64` | 4 个 4 B 字 |
| 5 | EI 范围、HIGH 重载、派生值 | 5 个代码站点 + **27 条数据记录** | 依赖 Step 2 |
| 6 | 普通 ISO 波轮映射 EI | `0x223A618`（4 B） | — |
| 7 | LV 底部 ISO 数值条 | `0x292CBA0`、`0x19DB9D4`、`0x292CAA4` + 80 B 岛 | 实验 |
| 8 | 普通 ISO/AUTO 改 Base | `0x3304D0C`、`0x3300D44` + 560 B 岛 | 实验 |

**依赖链**：

```
Step 0 ──> Step 1 ──> Step 2 ──> Step 3 ──> Step 5 ──> Step 6
                       │                    │
                       └──> Step 4 ─────────┤
                                            ├──> Step 7
                                            └──> Step 8
```

**必须按依赖顺序做，每步单独验证**（文档原文：
「EI 显示不对时，三层是三种不同的现象：菜单没有说明第一层没成；
能选但面板显示 `—` 说明第二层没成；面板能开但 HIGH 档黑屏说明第三层没成。三层连着做，就只能猜。」）

### 2.3 关键差异：Step 3 只能 RAM 补，不能文件补

我们实测发现：

```
0x8D915E8 > 文件大小 0x54E6C98（appFw.so = 89,027,992 B）
→ 该地址不在任何 LOAD 段
→ 是运行时地址（AP 基址 + ELF VA 之后的结果）
```

**所以**：Step 3 的 `26 → 19`（HIGH 基准）**只能在内存里改**。
这也是为什么纯文件补丁**永远做不出完整 EI** 的硬原因之一。

### 2.4 我们做的文件补丁版，实际覆盖了哪些

```
Step 4  4 处  ✅ 完整（标题阶梯）
Step 5  3 处  ✅ 部分（ldr → mov，但 27 条数据记录未做）
Step 6  1 处  ✅ 完整（波轮）
─────────────────────────
Step 0/1/2/3   ❌ 未做（需要运行时指针 / 114 对表 / RAM 地址）
```

**所以那个产物的真实定位是**：
> **证明「改了 AP 代码后壳校验仍能全层重算通过」**，
> 不是「EI 已解锁」。

## 第三部分：为什么 EI 测试固件不下放

### 3.1 技术原因

| # | 原因 | 说明 |
|---|---|---|
| 1 | **fastboot 防砖保护未测试** | 写入失败/半截态下能否恢复，没有实测 |
| 2 | **完整回滚方案未验证** | R2/R3 阶梯只有上游文档，我们自己没跑过 |
| 3 | **fastboot 工具未到位** | 社区工具只有 `oem partition dump`（读），没有写 |
| 4 | **ext2 被 debugfs 重写** | 我们的 EI 版有 242,633 个 4096 块差异（块重新分配），不是干净的 36 字节改动 |
| 5 | **只有壳校验通过，没有真机验证** | `a6700_v201.DAT` 真机验证过，EI 版**没有** |

### 3.2 第 4 条要特别说明

`a6700_v201.DAT`（纯版本号版）：**只 2 个 4096 块差异** —— 干净。
`a6700_v201_ei.DAT`（EI 版）：**242,633 个 4096 块差异** —— 因为 `debugfs write`
是「删了再写」，导致 ext2 块重新分配。

**壳校验只认 `part_image.sum` 里的 CRC**，所以 PASS；
但 `nflasha15` 的**内部布局已非原厂**，如果有其它未发现的校验，这里就是风险点。

**干净的只改 36 字节的做法**：用 `debugfs -R "blocks"` 找到数据块，
再用 `dd` 原地覆盖那 9 × 4 字节。这一版没做。

### 3.3 下放的条件（做到这些才能放）

- [ ] fastboot 写通道实测通过（`wbi rewrite` 自检 `verify=OK`）
- [ ] 防砖：写入失败时能恢复到原状，实测验证
- [ ] 完整回滚：R2 → R3 → R4 全链路跑通
- [ ] `nflasha15` 用 `dd` 原地改（只动 36 字节，不动 ext2 布局）
- [ ] 真机验证：能启动、能进菜单、至少一个 Step 生效

**目前只做到「壳校验 PASS」，前四项一个都没有。**

### 3.4 现在能公开什么

| 内容 | 公开 | 理由 |
|---|---|---|
| 校验器 `cst_verify.py` | ✅ | 纯读取，无风险 |
| 三层校验的算法与数值 | ✅ | 学术价值，无操作风险 |
| v2.01 识别层验证（真机照片） | ✅ | 已实测，现象明确 |
| 回滚方案与工具链说明 | ✅ | 防砖知识，应公开 |
| RAM 补丁的 Step 表与依赖 | ✅ | 上游已公开的机制说明 |
| 重打包脚本 | ❌ | 闭环未完成 |
| 改动版固件 | ❌ | 未真机验证 |
| 114 对计数表 / 27 条数据记录 | ❌ | 上游未公开，我们也没有 |

## 第四部分：结论

1. **v2.01 改动版不需要回滚** —— SD 卡上的独立文件，从未写入相机
2. **若真写入，回滚靠 R0（官方包）→ R2（反向写 827 B）→ R3（写回 WBI 头）**
3. **EI 的正确打开方式是 RAM 补丁（Step 0–8），不是改固件**
4. **Step 3 的 HIGH 基准只能在内存改**（地址超出文件范围）
5. **EI 文件补丁版不下放，因为防砖与回滚都未验证**
6. **防砖第一道闸是 `wbi rewrite` 自检** —— 写回原样数据看 `verify=OK`

**下一步（fastboot 工具到位后）**：
```
1. wbi.py hdr          确认 WBI2 / sections=1314 / sector=512
2. wbi.py rewrite      写通道自检，必须 verify=OK
3. wbi.py clear        备份 + 清零（先确认 orig512= 已落盘）
4. 拔电池冷启动        验证仍能启动
5. wbi.py restore      写回，验证恢复
6. —— 以上全部通过，才谈真正的固件修改
```
